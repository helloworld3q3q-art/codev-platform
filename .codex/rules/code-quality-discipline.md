# 代码质量纪律（AI 写码红线）

> 沉淀 2026-06-13 一轮:AI 多次被用户当场纠"堆代码 / 嵌套太深 / 死代码兜底 / 偷懒用错误技术理由延后"。
> 这些是**写码时的硬约束**,不是 nice-to-have。每条都附当日真实反例。

---

## 一、反面清单（命中即重写,别提交）

| 反模式 | 当日反例 | 正确做法 |
|---|---|---|
| **热路径堆过程式代码 + 并行结构** | merge 循环里塞 `node_origin` 并行 dict(与 `node_seen` 重复)+ 深嵌套 `elif` 做碰撞检测 | 复用已有结构;检测/统计这类横切逻辑抽出去,别塞进热循环 |
| **嵌套 ≥4 层** | `try→for repo→for result→for node→if` 五层 | 抽 `_collect_merged`/`_merge_result` 等单一职责小函数,主体降到 1-2 层 |
| **写"根治后即死"的兜底** | 先加跨仓碰撞 WARN 兜底,下一步又做根治(RepoScope)→ WARN 成死代码 | 要根治就直接根治;兜底只在"这轮确实不根治"时才加,且根治时同步删 |
| **未接线 flag / 未来代码** | （workflow §8）加默认 None 的参数却无调用方 | 加参数必同 PR 接线有真实调用方;否则不加 |
| **用错误技术理由给"不做"找台阶** | 主张"③ 必须耦合 RBAC + 必然未接线 flag 故延后"——被专家证伪(有 store 外零耦合做法),且顺手漏了真 bug(audit 扫空 / A2 悬空边) | 判"不做"前先证实理由;诚实区分"低价值"与"做不了";延后不等于不找相邻真问题 |
| **重复造真值源** | 想再加一份"前端 kind"集合 / 新 config 键 | 复用单一真值源:`internal_secret` 复用不新增键;软节点判定用 `schema.is_soft_node_kind`;"项目→仓根"用 `core.repos` |

## 二、正面原则（落每次改动）

1. **单一职责 + 内聚单元**:跨切面概念收进一个单元,对外只暴露窄接口。例:`RepoScope` 把"仓 tag 编码/还原"写侧 `localize` + 读侧 `resolve` 收一处,共用一份映射不漂移。
2. **低耦合 / 依赖方向**:下层不 import 上层。例:graph 层不 import web;allowlist/登记表这类上层数据由**顶层(CLI/工厂)组装后以中性 `set`/`callable` 注入**,graph 只收纯数据。
3. **走已有扩展点,不在核心加分支**:registry / Protocol / 声明属性 / 注入式。加能力 = 加一条注册 / 一个策略,不改驱动与既有分支。例:`UsageResolver` 策略、embedder registry。
4. **可扩展但不过度设计**:**必要才上设计模式**。`RepoScope` 用类(有跨调用状态)合理;`reconcile_orphan_pids` 纯函数足矣,别硬套类。
5. **契约对称不破**:sqlite/pg 双后端契约方法不加单边空转字段;改一边必对称(或证明另一边语义 no-op 且不破抽象)。
6. **健壮 / 高可用**:门禁、后台、读路径 fail-soft —— 失败返结构化空结果不崩(例 `audit_all_stores` pg 不可达返空报告不阻断 push),不把瞬时尖峰升级成硬失败。

## 三、PR 自检

- [ ] 最深嵌套 ≤3 层?能抽小函数降下来吗?
- [ ] 新加的参数 / flag 这个 PR 内有真实调用方?(无 → 删)
- [ ] 这轮加的兜底,会不会被同轮/下轮的根治变成死代码?
- [ ] 有没有重复造真值源 / config 键 / kind 集合?能复用现成的吗?
- [ ] 下层有没有 import 上层?跨层数据是不是注入而非耦合?
- [ ] 判"延后/不做"时,理由经得起证实吗?有没有顺手漏掉相邻真问题?
- [ ] sqlite/pg(或多实现)契约是否对称?
