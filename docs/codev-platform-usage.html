0. 架构总览（先读）

平台 = 服务端（三套 MCP 知识平面 + agent + memory/PG + 网关）常驻一处；开发机不跑服务，只通过 .mcp.json 连服务端。Git（Gitea）是唯一传输：开发机 push → 服务端 webhook 收到 → 服务端 pull 自己的 clone → reindex。所以开发机和服务端在不在同一台机器都无所谓。

开发机（Windows / Mac / Linux，任意） │ ① git push ② Claude Code 的 .mcp.json (SSE) ▼ │ Gitea（git 中心） ▼ │ ③ push webhook 服务端 MCP 端点（同机 127.0.0.1:19xxx / 跨机 https://域名） ▼ 服务端 codev-webhook ─→ reindex 队列 ─→ worker：git pull clone → 重建 chroma/codegraph/cross-link
组件端口（默认本机）systemd unit作用
platform-docs（chroma 文档检索）19083codev-mcp-platform-docs语义检索文档/规则
cross-link（跨层链路）19086codev-mcp-cross-link表↔接口↔代码链路
codegraph（代码图谱）19091codev-mcp-codegraph符号/调用/影响面
reindex worker—codev-reindex消费重建队列（先 pull 后索引）
webhook 接收器19099codev-webhook收 Gitea push → 入队
agent HTTP（可选）8848codev-agentLLM 问答 /chat
时钟重同步—codev-clock-resync.timer纠 WSL 睡眠后漂移
端口都是 config 驱动；本文以本机默认 19xxx 为例。下文命令默认在服务端（WSL）执行，除非注明"开发机"。

1. 配置文件

唯一用户级配置：~/.codev-platform/config.json（每台机器各一份，不进 git）。仓内 config.example.json 只是样板。优先级：env > 此文件 > 代码默认。

Windows 访问 WSL 那份：\\wsl.localhost\Ubuntu\home\helloworld\.codev-platform\config.json

段关键字段说明
modelsembed_path / embed_device / reranker_path / reranker_device / reranker_dtype(auto/fp16/bf16/fp32) / embed_batch_size显卡参数。换机器（小卡↔服务器大卡）只改这段
dataplatform_data_dirchroma/sqlite/索引数据根
daemon / mcpport(19083) / cross_link_sse_port / codegraph_sse_port各 MCP 端口
webhookport(19099) / secret / allow_insecurewebhook 接收器
memorypg_dsn / recall_backend / conflict_policy记忆 PG（独立库 codev_platform_memory）
gatewayauth_mode(passthrough/token) / tokens鉴权；dev=passthrough，对外=token
deploymentmode(dev/prod)prod 下非 token 拒绝启动
projects.<id>repo_path / org_id / webhook_repo / codegraph_api_url每个接入项目一条（见 §7）

查看（敏感值脱敏）：

codev-platform config doctor --redact

真密钥（webhook.secret / memory.pg_dsn / agent...api_key / gateway.tokens）只写本机这份 ~/.codev-platform/config.json，绝不进 git；仓内 config.example.json 永远只放占位符。

2. 服务启动

开机已自起（§3）。手动一键拉起 + 等待全部就绪：

# 服务端（WSL）
codev-platform serve-mcp start --wait          # 拉起并等三套端点 OK（超时报具体原因）
codev-platform serve-mcp status                # 查四端点（DOWN 会显示原因：进程/依赖/端口/DB）

或一键完整 bootstrap（换机/重 clone 后）：

codev-platform bootstrap            # venv 检查 → serve-mcp start → codegraph link → memory init-db
codev-platform bootstrap --dry-run  # 只看会做什么

3. 自动启动（开机）

WSL 启用了 systemd，服务为 system unit，开机自动拉起（Windows 重启 → WSL 起 → 服务回来）。安装/重装 unit：

# 生成 unit 到 ~/codev-systemd/ 并打印安装命令
codev-platform serve-mcp install-systemd
# 安装 + enable（需 root）
sudo bash ~/codev-systemd/install.sh
# 时钟纠偏 timer（可选，纠 WSL 睡眠后漂移）
sudo systemctl enable --now codev-clock-resync.timer
WSL2 默认非开机自启整个发行版；如需 Windows 开机即拉起 WSL+服务，在 Windows 任务计划加一条开机运行 wsl -d Ubuntu -- true（触发 WSL 启动，systemd 随之拉起服务）。

4. 重启 / 停止

# 重启全部 MCP 服务（改了代码/config 后）
sudo systemctl restart 'codev-mcp-*' codev-reindex codev-webhook
# 单个
sudo systemctl restart codev-mcp-platform-docs
sudo systemctl restart codev-agent

# 停止（临时）
sudo systemctl stop 'codev-mcp-*' codev-reindex codev-webhook
# 永久停某个（不再开机起）
sudo systemctl disable --now codev-agent
chroma 重启后需预热：platform-docs 重启后约 30–60s 加载 Qwen 模型，期间 status 可能短暂 DOWN，预热完即 OK。

5. 状态 / 排查

codev-platform serve-mcp status     # 四端点 + DOWN 原因
codev-platform health               # 当前仓体检（含 chroma 新鲜度 / hook missed）
codev-platform health --all         # 全平台各项目 × 三库 + 记忆
codev-platform logs --service all --tail 50   # 聚合各服务日志
codev-platform metrics              # 调用数 / 错误率 / 审计 deny / 阈值告警
codev-platform metrics --prometheus # Prometheus 曝光格式（可被 node_exporter 抓）
现象处理
端点 DOWNserve-mcp status 看原因；进程没起 → serve-mcp start；预热中 → 等 30–60s
chroma daemon 崩 / 睡眠后乱sudo systemctl restart codev-mcp-platform-docs；时钟漂移 → wsl --shutdown（Windows 端）
查不到最新文档health 看 freshness；手动 codev-platform reindex

6. 开发（连接平台）

开发机不跑服务，业务仓 .mcp.json 走 type:sse 连服务端。

同机（开发机 = WSL 宿主）

用 127.0.0.1:19xxx（Windows 经 wslrelay 转发到 WSL）。.mcp.json 形如：

{
  "mcpServers": {
    "platform-docs": { "type": "sse", "url": "http://127.0.0.1:19083/sse?project_id=<你的项目>" },
    "cross-link":    { "type": "sse", "url": "http://127.0.0.1:19086/sse?project_id=<你的项目>" },
    "codegraph":     { "type": "sse", "url": "http://127.0.0.1:19091/sse?project_id=<你的项目>" }
  }
}

在业务仓目录开 Claude Code → /mcp 看三套已连接。不会在开发机本地 spawn 任何服务。

跨机（服务在别的服务器）

一条命令把 .mcp.json 改成指向服务器（见 §10），URL 变 https://平台域名/<服务>/sse?project_id=...。

开发机用 127.0.0.1（同机）或服务器域名（跨机），不要用 WSL 的 VM IP（172.31.x，可能被 VPN/Clash 拦）。

7. 业务项目接入

让平台开始服务一个新项目（以 my-app 为例）：

# A. 业务仓里建 project 标识（开发机或服务端均可）
cd <业务仓> && codev-platform init my-app          # 生成 .claude/project.json
codev-platform register                            # 登记进 platform_meta/projects/

# B. 服务端 config.json 注册（运行时路由 + webhook 映射），projects 段加：
#   "my-app": {
#     "repo_path": "/home/helloworld/work/my-app",        # 服务端的 clone 路径
#     "org_id": "default",                                  # 多 org 时填真实 org
#     "webhook_repo": "<owner>/my-app"                       # Gitea 仓 owner/name，供 push 映射
#   }

# C. 服务端首次索引
PLATFORM_PROJECT_ID=my-app codev-platform reindex   # 或 python -m codev_platform.chroma.indexer
codev-platform codegraph link --project my-app      # codegraph 数据联接（如适用）

# D. 业务仓 .mcp.json 走 SSE（?project_id=my-app），见 §6
服务端要有该项目的 clone（repo_path 指它）。开发机另有自己的工作副本，两者经 Gitea 同步。

8. 更新（push 后自动 reindex）

配好 webhook（§9）后全自动：

开发机 git push → Gitea → push webhook → 服务端 codev-webhook → reindex 队列 → worker：git pull 服务端 clone（--ff-only，追到你 push 的状态）→ 重建索引

所以开发机改完 push 到 Gitea 即可，服务端自动把它的 clone 拉到最新再重建索引。

验证更新到没：

codev-platform health          # 看 "chroma freshness: index newer than latest doc" = 已更新
codev-platform logs --service reindex --tail 20
# 或 MCP codegraph_status 的 last_indexed_at

手动更新（不走 webhook 时）：

cd <服务端 clone> && git pull && codev-platform reindex

9. Git webhook 配置

结论：建 webhook 只改配置，不改代码。 Gitea / GitLab 两套验签+解析（provider）平台已内置，给某仓接 webhook = ① 服务端 config 加一条映射 + ② 在 Gitea 仓页面/API 建一个 hook。只有接全新 VCS（GitHub / Gitee 等，目前未内置）才需写一个 provider + 注册一行代码，server/队列/映射零改。

让某仓 push 后自动 reindex，两步（每个项目独立、可分开增量做）：

① config 映射（服务端 config.json，纯配置）

该项目 projects.<id>.webhook_repo = "<owner>/<repo>"（Gitea 仓全名，供 webhook 把 push 映射回 project_id）。

② Gitea 仓建 webhook（两种方式，二选一）

方式 A — 网页点选（推荐，最直观）

  1. 进仓库 → Settings → Webhooks → Add Webhook → 选 Gitea
  2. Target URL 填 http://127.0.0.1:19099/gitea（Gitea 与 webhook 同机；跨机填反代地址）
  3. HTTP Method = POST；Content Type = application/json
  4. Secret 填入 config 的 webhook.secret（两边一字不差，否则验签 401）
  5. Trigger On 选 Push Events，勾 Active → Add Webhook 保存
  6. 保存后点该 webhook 的 Test Delivery 验证；或真 push 后看 codev-platform logs --service reindex
网页字段填什么
Target URLhttp://127.0.0.1:19099/gitea（同机）/ 反代地址（跨机）
HTTP MethodPOST
Content Typeapplication/json
Secret= config webhook.secret（HMAC 验签，必须一致）
Trigger OnPush Events
Active勾上

方式 B — API（适合脚本/批量建），效果同方式 A。把 <...> 占位符替换成你的值：

curl -u '<Gitea用户名>:<密码>' -X POST \
  http://localhost:3000/api/v1/repos/<owner>/<repo>/hooks \
  -H 'Content-Type: application/json' -d '{
    "type":"gitea",
    "config":{"url":"http://127.0.0.1:19099/gitea","content_type":"json","secret":"<webhook.secret>"},
    "events":["push"],"active":true }'
curl 占位符替换成例子
<Gitea用户名>:<密码>登录 Gitea 的账号:密码helloworld:******
localhost:3000Gitea 地址:端口（默认 3000）不改就这样
<owner>/<repo>仓库全名 owner/namehelloworld3q3q/platform
<webhook.secret>config 里 webhook.secret 同一值两边必须一致

验证：在 Gitea webhook 页点 "Test Delivery"，或真 push 后看 codev-platform logs --service reindex。当前已配仓：platform / codev-platform / codev-platform-widget。

Gitea 回环调用 webhook 需 app.ini 的 [webhook] ALLOWED_HOST_LIST = loopback（已配）。

10. 部署到独立服务器

把服务从"和开发机同机的 WSL"搬到独立服务器，只需在服务器复刻服务端，开发机改指向：

服务器侧

1. 装 Python + 重建 venv（requirements-runtime.txt）；如用 GPU 装对应 torch
2. clone 各项目仓到服务器（repo_path 指它们）
3. 配 ~/.codev-platform/config.json（models/data/ports/memory.pg_dsn/projects）
4. 建 PG 独立库 codev_platform_memory + codev-platform memory init-db
5. codev-platform serve-mcp install-systemd && sudo bash ~/codev-systemd/install.sh
6. 对外：caddy/nginx 反代 + TLS（见 docs/plans/.../remote-access-reverse-proxy）
   开 token 模式：codev-platform gateway mode token + 建 token

开发机侧（指向服务器）

# 把业务仓 .mcp.json 的 url 改成服务器地址（按服务名做路径前缀）
codev-platform gateway client-url --base https://平台域名 --repo <业务仓>
# 注入 token（token 模式）
codev-platform gateway client-auth --repo <业务仓>
export PLATFORM_TOKEN='<token>'        # 重启 Claude Code

数据备份/恢复：codev-platform backup（pg_dump + data + 保留 N 份）；详见 PG 持久化 / 备份 runbook。

11. Agent 问答（可选）

用平台的 LLM 问答（/chat、Web playground）才需要：

# 服务端装 agent 依赖 + 填 provider key（~/.codev-platform/config.json 的 agent 段）
.venv/bin/pip install fastapi uvicorn
# config: "agent": { "provider": "deepseek", "providers": { "deepseek": { "api_key": "..." } } }
sudo systemctl restart codev-agent          # 读 key
curl -s -X POST http://127.0.0.1:8848/chat -H 'Content-Type: application/json' \
  -d '{"question":"...","project_id":"<项目>"}'

只读 Web playground：docs/playground/index.html，平台地址填 http://127.0.0.1:8848。
