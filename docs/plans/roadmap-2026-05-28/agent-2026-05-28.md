# Agent 开发 Plan(2026-05-28,v2 — HTTP 服务 + 多模型)

> **前提**:平台已提供 agent 的"感官"—— 3 套能力(platform-docs 语义检索 / codegraph 代码图谱 / cross-link 跨层链路,皆有 MCP + Python API)+ 跨平台 CLI 控制平面。缺的是"大脑回路"(LLM + 循环 + 目标)。
>
> **v2 定调(2026-05-28 用户拍板)**:agent 做成 **HTTP 服务**(可部署、headless、对外/无人值守),**大脑可插拔**(Claude / GPT / DeepSeek / 通义千问),配置驱动切换。
>
> **核心原则**:核心(循环 + 工具 + provider 抽象)与暴露层(HTTP / CLI)解耦;provider 抽象与具体厂商解耦。先核心,后壳,后多 provider。

## 一、技术方案

### 1.1 分层架构

```
HTTP client(web / CLI / 其它服务 / cron)
        │  HTTP REST + SSE 流式
┌── Agent 服务  codev_platform/agent/ ───────────────────────────┐
│  service.py   FastAPI daemon: /chat /task /health /providers     │
│  loop.py      agent 循环 (plan→tool→observe→act→stop, step 上限)  │
│  brain/       LLM provider 抽象层(可插拔)                        │
│    base.py        LLMProvider ABC: chat() / stream(),统一中性     │
│                   tool-call 格式(agent loop 只认这套中性格式)    │
│    anthropic.py   Claude(Anthropic SDK, tool_use blocks)         │
│    openai_compat.py  GPT / DeepSeek / 通义千问 共用一个适配器      │
│                   (三家都是 OpenAI chat-completions 格式,         │
│                    靠 base_url + model + key 区分)                │
│    registry.py    provider 工厂:按 config 选 + 注册              │
│  tools.py     工具封装(调 MCP client 或 in-process Python API)   │
│  memory.py    会话 / 上下文(检索压小 + 阶段 summary)            │
│  secrets      多家 API key 走 env / .env(不进 git)              │
└──────────────────────────────────────────────────────────────┘
        │
 平台能力: chroma 检索 · codegraph · cross-link · dirty-check(判索引可信)
```

### 1.2 多模型抽象(关键设计)

**洞察**:GPT / DeepSeek / 通义千问**都提供 OpenAI 兼容的 chat-completions 接口**(DeepSeek、Qwen/DashScope 均有 OpenAI-compatible endpoint)。Claude 是自有 SDK(tool_use 格式不同)。所以实际只需 **2 个适配器**:

| 适配器 | 覆盖 | 接口形态 |
|---|---|---|
| `anthropic.py` | Claude | Anthropic Messages API(`tool_use` / `tool_result` blocks)|
| `openai_compat.py` | **GPT + DeepSeek + 通义千问** | OpenAI `tools` / `tool_calls`,参数化 `base_url`+`model`+`key` |

**统一中性 tool-call 格式**:agent loop 只认一套中性的 `{tool_name, args}` / `{tool_result}` 结构;各 provider 适配器负责**翻译**到/从自己的原生格式。这是抽象层的核心工程点(见难点 §三.1)。

### 1.3 配置驱动 provider 选择(契合平台哲学)

```jsonc
// ~/.codev-platform/config.json(在用户主目录,不在 git 仓 → key 不会被 commit)
"agent": {
  "provider": "claude",          // claude | gpt | deepseek | qwen
  "model": "claude-opus-4-7",
  "max_steps": 12,
  "providers": {
    "claude":   { "api_key": "" },  // 留空则走 env ANTHROPIC_API_KEY
    "deepseek": { "base_url": "https://api.deepseek.com",        "model": "deepseek-chat", "api_key": "" },
    "qwen":     { "base_url": "https://dashscope.../compatible", "model": "qwen-max",      "api_key": "" },
    "gpt":      { "base_url": "https://api.openai.com/v1",       "model": "gpt-4o",        "api_key": "" }
  }
}
```

换模型 = 改一行 config + 配好对应 key。加新厂商 = 若 OpenAI 兼容则只填 config;否则加一个适配器。**跟"加项目零改代码"一个路子。**

#### secrets 方案 — env > config 双通道(2026-05-29 定)

key 解析顺序:**env 变量 > `config.agent.providers.<name>.api_key` > 报错**(复用 `core/config.py:env_or_config()`)。
- 本机开发:直接填 config.json 的 `api_key`(方便)
- 服务器 / CI / 对外部署:`ANTHROPIC_API_KEY` / `OPENAI_API_KEY` / `DEEPSEEK_API_KEY` / `DASHSCOPE_API_KEY` 走 env 覆盖,config 留空

**4 条红线**:
1. **绝不进仓** — `config.example.json` 只放占位符 + 注释,真 key 仅在用户本机 config.json
2. **绝不回显** — `/providers` 只返 `configured: bool`,不返 key;日志 / trace 不打印 key
3. **save_config 不外泄** — 回写保留 key,错误信息不 dump 整个 config
4. **文件权限** — config.json 用户只读(`chmod 600` / Win ACL)

### 1.4 工具接入

- **backend 策略(2026-05-29 定,按现状)**:`cross_link` 走 **in-process**(`CrossLayerDB`,最省);`search_docs`(chroma)走 **daemon HTTP/MCP**(复用暖模型,免在 agent 进程再加载 0.6B);`codegraph` **只有外部 MCP**(无 in-process API)→ 走 MCP client。tool 层对 loop 暴露统一 `Tool` 抽象,backend 差异封在各 tool 内部。
- 决策前 `dirty-check` 判索引可信;dirty 命中则回读真实文件(workflow §2.2 教训)。
- 工具选型逻辑喂 workflow §3.2 映射(找代码→codegraph / 找规则→search_docs / 找链路→cross-link)。

### 1.7 接口规划

#### A. HTTP API(对外契约)

```
POST /chat                  同步问答(A 能力主入口)
  req:  { question: str, session_id?: str, provider?: str, max_steps?: int }
  resp: {
    session_id: str,
    answer: str,                       # markdown,带文件:行号证据
    evidence: [{ type: "codegraph"|"cross_link"|"doc", ref: str, snippet: str }],
    steps:    [{ thought: str, tool: str, args: obj, result_summary: str }],
    usage:    { provider: str, model: str, input_tokens: int, output_tokens: int },
    stop_reason: "answered"|"max_steps"|"error"
  }

POST /chat/stream           SSE 流式;event: step | token | done | error
GET  /health                { status, provider, model, index:{ fresh, last_build, dirty } }
GET  /providers             [{ name, model, configured: bool }]   # configured=key 是否在位
```

鉴权:P0 本地无鉴权;P2 加 API key header(配置驱动)。

#### B. 内部抽象接口(provider 与 tool 的契约,决定多模型可插拔)

```python
# brain/base.py — 中性类型 + provider 抽象
@dataclass class ToolCall:    id: str; name: str; args: dict
@dataclass class ToolResult:  call_id: str; content: str; is_error: bool = False
@dataclass class Message:     role: str; content: str | None; tool_calls: list[ToolCall] = []; tool_call_id: str | None = None
@dataclass class AssistantTurn: text: str | None; tool_calls: list[ToolCall]; stop_reason: str; usage: dict

class LLMProvider(ABC):
    @abstractmethod
    def chat(self, system: str, messages: list[Message], tools: list[dict]) -> AssistantTurn: ...
    @abstractmethod
    def stream(self, system, messages, tools) -> Iterator[Event]: ...
    # 每个适配器只干一件事:中性 Message/ToolCall ↔ 自家原生格式 双向翻译

# tools/base.py — 工具抽象
class Tool(ABC):
    name: str
    description: str
    input_schema: dict          # JSON Schema,转给各 provider 的 tool spec
    @abstractmethod
    def run(self, args: dict) -> ToolResult: ...

# loop.py — 循环契约
class AgentLoop:
    def __init__(self, provider: LLMProvider, tools: list[Tool], max_steps: int): ...
    def run(self, question: str, history: list[Message]) -> AgentResult: ...
```

**可插拔保证**:loop 只依赖 `LLMProvider` + `Tool` 抽象,只认中性类型;换模型只换 `registry` 返回的 provider 实例,loop / tools / service **零改**。这就是 P1 加 3 家模型不动核心的根据。

## 三、难点(诚实)

| # | 难点 | 为什么难 / 对策 |
|---|---|---|
| 1 | **tool-call 格式跨厂商归一** | Anthropic `tool_use` vs OpenAI `tool_calls`,各有怪癖(并行调用、JSON schema 严格度、stop_reason 语义)→ 中性格式 + 每家适配器双向翻译 + 各家 fixture 测试 |
| 2 | **能力参差** | GPT/DeepSeek/Qwen 的 tool-use 可靠性、long-context、指令遵从各不同 → agentic prompt 可能要 per-provider 微调;弱模型加 retry / 格式校验 |
| 3 | **HTTP 服务工程** | 鉴权 / 并发 / SSE 流式 / 会话状态 / 超时 / 取消 → FastAPI + 每会话 task,流式用 SSE;先单用户跑通再加并发 |
| 4 | **secrets 管理(多 key)** | Claude/GPT/DeepSeek/DashScope 多把 key + 数据源 token → **平台现缺**,部署前必须定 env/.env 方案,不进 git |
| 5 | **循环可靠性** | 跑偏/死循环/幻觉 → step 上限 + 停止条件 + 错误恢复 + 每步可观测(trace 落盘)|
| 6 | **上下文管理** | 长任务爆 context → 检索只拉相关 chunk(平台强项)+ 阶段 summary;不同模型 window 不同 |
| 7 | **eval** | 怎么知道答得对 → golden 问答集 + 人工抽检;接上已有 pytest;**多模型还要横评**哪家在本仓任务上更准 |
| 8 | **成本 / 限流** | 各家计费 + rate limit 不同 → 检索压小上下文 + 缓存 + 限 step + 按 provider 配额 |
| 9 | **写安全(P2/P3)** | 自动改代码风险 → dry-run + 人在环 + 测试必过 gate + 可回退;服务端绝不自动 push |

## 四、第一步(P0 最小可部署服务)

1. 建 `codev_platform/agent/` 骨架:`brain/{base,anthropic,registry}.py` + `loop.py` + `tools.py` + `service.py`。
2. `brain/base.py` 定中性接口(即使先只接 Claude,也按抽象写,P1 加 openai_compat 零改 loop)。
3. `tools.py` 先封 3 个只读工具:codegraph 查询 / cross-link 查询 / search_docs。
4. `service.py`:FastAPI `/chat`(收问题→loop→带证据答)+ `/health` + `/providers`。
5. 配置:`config.agent.*` + `ANTHROPIC_API_KEY` 走 env。
6. 验证:`curl /chat` 问一个本仓代码问题,看是否调对工具 + 证据可追溯 + step 不失控。

P0 跑通 → P1 加 `openai_compat.py`,config 切 DeepSeek/Qwen/GPT 各验一次。
