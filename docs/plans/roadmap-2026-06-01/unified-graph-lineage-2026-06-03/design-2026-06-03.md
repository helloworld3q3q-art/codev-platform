# 技术方案:统一图谱·全栈血缘收敛 (2026-06-03)

## 1. 目标

单系统打通四层数据血缘 + 服务链路,**一套实现**:

```
上游数据(采集/pipeline 写库函数) → SQL(表/字段) → 后端(端点) → 前端(路由/接口调用)
        writes_table              defines_column      reads_table        calls_api
```

随便点一张表,能上溯"哪个采集任务写的",下追"哪个后端读它、哪个前端页面展示"。

终态:`cross_link` 适配器(`graph/adapters/cross_link.py`)退场,上述全部由 stack 插件 +
核心 linker 产出,统一 store 是唯一真值,统一图谱是唯一页面。

## 2. 生产者归属(零重叠)

每个 `kind × 语言/框架` 只有一个 owner,这是不再重复的根本契约。

| 层 / 边 | kind | owner 生产者 | 现状 |
|---|---|---|---|
| 上游数据 | `backend_function`(写库函数) | sql 插件(DML 维度) | ❌ P2 |
| 上游→表 | `writes_table` | sql 插件(扫 INSERT/UPSERT + 归属函数) | ❌ P2 |
| SQL/DB | `db_table` / `db_column` | sql 插件(DDL) | ✅ |
| 表内 | `defines_column` | sql 插件 | ✅ |
| 表→后端 | `reads_table` | sql 插件(扫 SELECT + 归属函数) | ❌ P2 |
| 后端 | `backend_endpoint`(py) | fastapi 插件 | ✅ |
| 后端 | `backend_endpoint`(java) | **spring 插件** | ❌ P1 |
| 后端 | `backend_endpoint`(node) | node 插件 | ✅ |
| 后端→前端 | `calls_api` | **核心 linker pass** | ❌ P3 |
| 前端 | `frontend_route` / `frontend_api_call` | react / vue 插件 | ✅ |

> 已有资产可复用,**不重新开发**:`_stack_scan.link_api_calls()` 已实现前端↔后端 URL 匹配
> (与 `cross_link/linker.py` 同逻辑),P3 只需把它接进 ingest 流程,无需重写。

## 3. 核心 linker pass(P3 的架构点)

现状:`graph.ingest.ingest_project()` 跑完各插件 `upsert_result` 就结束,**没有跨插件步骤**。
而 `calls_api`(前端→后端)天生跨插件(react 只看前端、fastapi 只看后端,谁都连不了)。

方案:在 `ingest_project` 末尾加 **linker pass**:

```
1. 各插件 analyze → upsert 进 store(现有)
2. linker pass:从 store 读回全量节点 →
   - link_api_calls(frontend_api_call, backend_endpoint) → calls_api 边
   - (P2 起)reads/writes_table 由 sql 插件在 analyze 内直接产, 不在此 pass
3. 以合成插件名 `builtin.linker` upsert 这批跨层边(plugin 归属隔离, 幂等可重跑)
```

linker 产出独立挂 `builtin.linker` plugin 名 → 重跑 ingest 幂等替换,不与各栈插件互相覆盖。

## 4. 上游 / DB 访问节点(P2)

sql 插件现在只扫 `CREATE TABLE`(DDL)。扩 DML:

- 扫 `.py` 里 `cursor.execute("INSERT/UPDATE/SELECT ... <table>")` / ORM 写读 → 解析目标表 + **所在函数**。
- **上游节点 = 写库的函数/模块**(语言无关:有 py 写库就 py 函数;别的语言同理;系统无上游层则自然不产)。kind 用 `backend_function`,meta 标 `role=writer|reader`。
- 边:`function --writes_table--> db_table`(INSERT/UPSERT/UPDATE)、`function --reads_table--> db_table`(SELECT)。表名 lower 归一,命中 sql 插件已建的 `db_table` id(`<pid>:db_table:<name_lower>`)。

### 已知 seam:表→端点的"最后一跳"

SQL 通常在 repo/service 函数里,不在 endpoint 本身。`backend_function --reads_table--> table` 能建,
但 `backend_endpoint --calls--> backend_function` 这一跳需要调用图。处理:

- **默认(本轮)**:函数级粒度即可 —— 血缘到"哪个函数读写表"已满足需求;endpoint 与 reader 函数
  同文件/同模块时加弱 `calls` 边(启发式,confidence<1)。
- **后续(非本轮)**:要精确 endpoint→func→table,走 codegraph 桥接(codegraph 支柱已有全调用图),
  不在统一 store 重做方法级。

## 5. cross_link 退场(P4,parity 门控)

直接删 → openclaw 图谱当场空(它现有 9118 跨层边、132 Java 端点全来自 cross_link)。顺序:

1. P1+P2+P3 让 stack+linker 产出 Java 端点 + 跨层边;
2. **parity 对账**:`stack+linker` 的 `backend_endpoint` 数、`calls_api` 连通数 ≥ cross_link 当前覆盖;
3. 达标 → 删 `graph/adapters/cross_link.py` + 注册点;下线 `跨层链路` 页 / `/cross-link/*` 冗余接口,
   功能并入统一图谱(按层筛选 + table-refs/endpoint-link 进节点详情面板)。

> codegraph / chroma 两支柱本轮**不动**。

## 6. 防复发(P4)

呼应仓库 assertion 文化,落两样:

1. `plugins` 加 `kind × 语言 → owner` 注册表(单一真值)。
2. 约定测试:扫统一 store,断言**同一 project 内同一 `(kind, name, file)` 不来自 >1 个插件**
   (除非声明 gap-filler 关系)。新加重复扫描器 → 测试红。

## 7. 不做 / 边界

- 不动 codegraph(代码方法级)、chroma(语义)两支柱。
- 不做跨项目/跨系统链接(per-project store 不变;那是"多组织"另一专题)。
- DML 解析第一版轻量(覆盖最常见 execute/ORM 写法),不追求全语法覆盖,但产出 schema 合法、id 可链接。
